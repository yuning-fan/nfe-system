### 二、选课与课表解耦

**诊断（与最初设想不同，记录下来避免重复分析）**
1. 「每人上课时间不同」**表结构早就支持** —— `school_timetable` 本就按学生存。问题在流程：唯一入口是从 `program_subjects.default_schedule` 复制模板，故人人相同；且无任何逐人编辑处。

### 二、学生列表与导出：默认排序 + 导出字段记忆修复

**默认排序**
- 需求：先看「还在项目里的人」，再按学号。同一轮内追加要求细分档位。
- `StudentList.tsx` 在 `dataSource` 里加默认排序：`statusRank` → `nfe_no` 升序，无学号排末尾。

- 页面列表与导出共用这一套档位，未拆成两份口径。

**导出字段记忆失效（bug 修复）**
- 现象：`ExportFieldsModal` 号称「选择会记住」，实际每次打开都是全选。
- 根因：localStorage 只存了 `selected`（勾中的列）。而「新增列默认选中」的逻辑判断的是「不在存档里的列」——**用户取消勾选的列恰好也不在存档里**，与「代码后来新增的列」无法区分，于是取消项每次都被勾回来。
- 修法：改存 `{ selected, known }`，`known` 记录保存那一刻存在过的全部列，只有不在 `known` 里的才算新增。`saveSelectedColumns` 相应加 `allTitles` 参数。
- 兼容旧的纯数组格式：认作「全都见过」（`known` 为空 → 不判定新增），保住用户已有的取消项，下次保存自动升级为新格式。
- 用 `npx tsx` 直接跑真实模块验了 6 个场景：无配置全选、取消项不被勾回、代码加列默认选中、代码删列不炸、旧格式兼容、坏数据回落全选，全过。

- **新文件**: 报告数据状态管理
- `fetchReports` — 查询 `reports` 表并通过 `profiles!reports_student_id_fkey` 外键关联获取学生 `full_name` 与 `avatar_url`

- **根本性修复**: 将所有 Supabase 调用从 `supabase.from(...)` 改为 `const db = supabase as any` 别名调用，统一解决 `never` 类型推断问题

### 📐 技术决策备注

#### 关于 `supabase as any` 模式

项目中 `@supabase/supabase-js` 的类型推断依赖于本地生成的 `database.types.ts`。由于当前项目**未运行 `supabase gen types typescript`** 生成类型文件，所有自定义表（`warning_letters`、`reports`、`students_info` 等）的 insert/update 参数都会被推断为 `never`。

**当前采用的临时方案**: 在每个 store 文件中声明 `const db = supabase as any`，将 Supabase 调用链的类型推断完全绕过。

**上线前应改为正确方案**: 运行 `npx supabase gen types typescript --local > src/types/database.types.ts`，生成完整的类型定义文件，让 Supabase client 获得正确的表级类型推断。
