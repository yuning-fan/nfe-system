## 2026-06-24 · Phase 16 · 风险评分自动算分引擎 + 晚自习点名

### 🎯 目标
把风险预警从"纯手动、全员绿 100"做到"客观指标自动算分 + 录入即时重算"。扣分动作分散到各角色面板，自动汇总到学管/admin 看板（设计见《风险评分系统_设计与TodoList》§3.5）。

### ⚙️ 算分引擎（核心）
- 新建 `src/lib/riskEngine.ts`：`computeRisk(studentId)` 按 15 天滚动窗口统计 缺勤(daily_checks 分 night_study/morning/tutoring/dorm_check) / 违规(violation_logs) / 警告信累计 / 证件临期 / 欠费 / 成绩低于阈值 → 算 `total_risk_score`（100 扣分制）→ 等级（≥85 绿 / 60–84 黄 / <60 红），硬触发（连续缺勤≥3天 / 第3封警告 / 证件≤7天）直接红。
- `recomputeRisk(studentId)` 写回 `students_info` + 等级变化记 `log_risk_changes`(trigger_type=`system_auto`)；`recomputeAll()` 全员重算。
- 接通既有录入：`ViolationLog`（登记/存档）、`useDailyCheckStore`（点名提交）、`useRiskStore.approveWarning`（改为交引擎重算，弃用旧固定扣分）。
- 风险页加「一键重算全员风险分」按钮（`RiskAlerts.tsx`，用于首次初始化/口径调整后刷新）。

### 🧍 晚自习点名（巡查，真功能）

## 2026-06-19 · Phase 12 · 员工账号管理

### 📋 概述

管理员可在系统内自助管理员工账号，不再依赖开发者手动写 SQL 建号。`/accounts` 从占位页换成真实功能页。

### ☁️ Edge Function `staff-admin`（service_role）

- 用 Supabase Auth Admin API 操作账号，`SUPABASE_SERVICE_ROLE_KEY` 仅存于函数环境，绝不下发前端。
- 调用方校验：必须是 admin（验证 JWT 对应 `profiles.role='admin'`），否则 403。
- 4 个 action：
  - `create`：`auth.admin.createUser`（自动确认邮箱）+ upsert profile；profile 写入失败则回滚删除 auth 用户，避免孤儿账号。
  - `update_role`：改 `profiles.role`。
  - `reset_password`：`auth.admin.updateUserById`。
  - `set_status`：停用/启用——置 `profiles.status` + `ban_duration` 真正阻断登录；禁止停用自己。
- 已端到端验证：admin 登录 → 建号 → 新账号可登录 → 角色/档案正确。

### 🖥️ 前端

- `store/useStaffStore.ts`：列表 + 4 个操作，统一通过 `supabase.functions.invoke('staff-admin')` 调用。
- `pages/Accounts/Accounts.tsx`（替换占位）：员工表（姓名/角色/电话/状态），行内改角色下拉、重置密码、启用停用；新建员工弹窗（姓名/角色/邮箱/电话/初始密码）。

## 2026-06-17 · Phase 5 · 核心业务模型重构 (Programs & Source)

### 📋 概述

本次变更旨在解决系统初期设计中将“商业来源（商务归属）”和“学习阶段（系统功能模块）”混为一谈的问题。现将二者解耦，确保逻辑准确，并为即将到来的大规模学生数据导入打好地基。

---

### 🏗️ 架构与数据库重构

#### 核心痛点与解决思路
**问题**：旧的 `programs` 表中存在如“绿通-Standard”、“名校散客”、“绿通转名校”等选项。这导致了逻辑混淆：“绿通”是一个商务来源概念（全包VIP），而“Standard (12月)”是一个学制概念。
**方案**：将业务拆分为两个独立维度：
1. **商务来源 (`source`)**：转移至 `student_enrollments` 表中。
2. **学习阶段 (`program_id`)**：净化 `programs` 表，使其仅表示纯粹的学制与阶段。

#### 具体的 DDL 变更
- 新增枚举 `enrollment_source`，包含 `green_channel` (绿通) 和 `agent` (散客)。
- `student_enrollments` 表新增 `source` 字段。
- `program_track` 枚举新增 `fast_track` 和 `university`。
- 重构 `programs` 表字典项，使其变为：
  - `预科-Standard (12月)`
  - `预科-Accelerated (5月)`
  - `预科-Fast-track (8月)`
  - `大学阶段-住宿监管`
- 清除了多余的历史废弃 Program 项。

#### 历史数据平滑迁移
- 针对 `student_enrollments` 中已存在的 37 条真实数据，编写了迁移脚本。
- 根据旧的 `program_id` 自动提取其商务属性更新至新加的 `source` 字段，并将他们安全地挂载到合并后的正确预科阶段上，做到了无损迁移。

---

### 🖥️ 前端页面与文档变更

#### 页面变更
- `src/pages/Students/StudentList.tsx`：在表格的“项目”列中，加入了“绿通”与“散客”的 Badge（Pill）动态渲染。
- `src/pages/Students/StudentDetail.tsx`：详情页顶部 Tag 及资料卡片新增 `source` 来源显示逻辑。

### 📐 技术决策备注

#### 关于 `supabase as any` 模式

项目中 `@supabase/supabase-js` 的类型推断依赖于本地生成的 `database.types.ts`。由于当前项目**未运行 `supabase gen types typescript`** 生成类型文件，所有自定义表（`warning_letters`、`reports`、`students_info` 等）的 insert/update 参数都会被推断为 `never`。

**当前采用的临时方案**: 在每个 store 文件中声明 `const db = supabase as any`，将 Supabase 调用链的类型推断完全绕过。

**上线前应改为正确方案**: 运行 `npx supabase gen types typescript --local > src/types/database.types.ts`，生成完整的类型定义文件，让 Supabase client 获得正确的表级类型推断。
