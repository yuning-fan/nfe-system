# 已知问题记录

## 0. ⚠️ PostgREST 嵌套查询外键歧义（已踩两次，必读）

**现象**：页面数据整块消失、无报错。如证件管理页（Documents）学生列表全空。

**根因**：`select('a, profiles(full_name)')` 这类嵌套查询靠**外键自动推断**关联路径。
一旦同一张表出现**第二个指向同一目标表的外键**，推断出现歧义，PostgREST 返回 `PGRST201`，
**整条查询失败**（不是只丢那一列）。而前端普遍写成 `const { data } = await ...; const list = data || []`，
`data` 为 null 被 `|| []` 静默兜掉 → 页面空白但控制台无明显错误。

**为什么难发现**：`tsc`、`npm run build`、migration **全都不报错**，只有真实发请求才暴露。

**已发生两次**：
1. `grade_records`（`student_id` + `recorded_by`）—— 历史遗留，因成绩表长期为空未被发现，
   直到 2026-08 录入陈亦凡成绩后才暴露（学管成绩页列表恒空）。
2. `students_info`（原有 `student_id`，2026-08-10 迁移新增 `nz_advisor_id`、`life_teacher_id`）
   —— 加字段引入的回归，打挂 13 处查询。

**规避**：
- 写嵌套查询**一律显式指定外键**：`profiles!student_id(full_name)`，哪怕当前只有一个关系。
- **任何 migration 加了指向已有关联表的外键后**，立刻全项目扫：
  ```bash
  grep -rn "<表名>" --exclude-dir=node_modules . | grep "profiles(" | grep -v "profiles!"
  ```
- 用 `.env.local` 的 anon key 直接 curl PostgREST 对比新旧写法，能立刻看到是否 `PGRST201`。

**当前已知有多个 FK 指向 `profiles` 的表（19 张）**：
`communication_logs`(staff_id,student_id) · `daily_checks`(staff_id,student_id) · `dcg_cases`(guardian_staff_id,student_id) ·
`grade_records`(recorded_by,student_id) · `leave_applications`(approver_id,student_id) · `log_hour_changes` · `log_risk_changes` ·
`medication_records`(dispensed_by,student_id) · `medications`(created_by,student_id) · `reports`(generated_by,reviewer_id,student_id) ·
`schedule_changes`(approver_id,requester_id) · `schedules`(student_id,tutor_id) · `school_timetable`(generated_by,student_id) ·
`student_documents`(student_id,uploaded_by) · `student_enrollments`(enrolled_by,student_id) ·
`students_info`(student_id,nz_advisor_id,life_teacher_id) · `study_follow_ups`(recorder_id,student_id) ·
`violation_logs`(reporter_id,student_id) · `warning_letters`(issuer_id,student_id)

> 2026-08-11 已将全项目裸嵌套显式化。新增查询请沿用 `profiles!student_id(...)` 写法。

## 1. 学生详情页跳转异常 (已解决)
**描述**：在学生列表中点击 “查看档案” 时页面会跳回首页（Dashboard）而不是进入学生详情页。

**根因**：`App.tsx` 中新加入的 `students/:id` 动态路由在本地开发服务器的热更新（HMR）未及时刷新，导致浏览器仍使用旧的路由表，匹配不到新路径，触发了 `*` 通配路由的 `<Navigate to="/" replace />` 重定向。

**临时解决方案**：
- 手动 **全页面刷新**（`Cmd+Shift+R` 或浏览器刷新按钮）后即可正常跳转。

**长期改进建议**：
1. 完成开发后 **重启** `npm run dev`，确保路由表完整加载。
2. 将路由结构变更记录在 **路由变更日志**，代码审查时提醒前端团队。

## 2. 角色账号体系设计决议
**描述**：关于是否需要为管理员、学生等角色创建独立的账号/密码。

**结论**：
- **管理员（admin）及其他后台管理角色（manager、tutor 等）**：**必须**拥有独立的 **email + password**，通过 Supabase Auth 登录，以便进行权限管理、RLS 策略维护和后台操作。
- **学生（student）**：当前业务仅由后台人员查看和编辑学生信息，无需学生自行登录。若后续需要学生自助查看风险评估、签到记录等功能，可在后续迭代中为学生单独创建账号并在 `profiles` 表中标记 `role = 'student'`。

**后续动作**：
- 在 Supabase **Authentication** 中为管理员等角色创建账号，并在 `profiles` 表中设置对应 `role`。
- 实现登录页面时，只针对后台角色提供登录能力。
