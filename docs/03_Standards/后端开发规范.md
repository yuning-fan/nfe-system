# NFE 项目：后端与数据库开发规范

本项目采用 **Serverless / BaaS 架构**，以 **Supabase (PostgreSQL)** 为核心。因此“后端开发”主要指代数据库模型设计、权限配置与边缘函数编写。

## 1. 数据库命名规范

*   **表名与列名**：一律使用 **snake_case** (小写下划线)，且表名使用复数。
    *   ✅ 正确：`students_info`, `created_at`
    *   ❌ 错误：`studentInfo`, `CreatedAt`
*   **主键**：默认为 `id`，若作为软关联外键引用时，以 `表单数名_id` 命名 (如 `student_id`)。
*   **时间戳**：固定使用 `created_at` 和 `updated_at`，类型统一为 `TIMESTAMPTZ` (带时区)。
*   **布尔值**：以 `is_` 或 `has_` 开头，如 `is_active`。

## 2. 视图与触发器 (Views & Triggers)

为了保证数据的绝对一致性，系统采用**“重数据库级计算，轻应用层计算”**的原则：
*   **汇总与统计字段**：严禁在业务表中直接写入经常变动的统计字段（如课时余额）。必须通过 `VIEW`（视图）实时聚合。参考 V4.1 架构中的 `v_course_remaining`。
*   **强一致性联动**：如审批通过后自动发送通知、课时核销后自动记录流水等逻辑，优先使用 PostgreSQL **Triggers (触发器)** 处理，确保即便越过前端直接改库，业务逻辑依然闭环。

## 3. 数据安全与访问控制 (RLS)

系统必须开启 Supabase 的 **Row Level Security (RLS)**。
所有请求到达数据库时，必须带上合法的 JWT 身份令牌。
*   **隔离原则**：
    *   学生 (`role = student`)：只能 `SELECT` 自己名下的记录 (`student_id = auth.uid()`)，禁止任何 `DELETE`。
    *   学管/教务 (`role = manager`)：可以进行全域的 CRUD 操作。
*   在前端代码中调用 API 前，务必确保 RLS 策略已覆盖目标表，否则将返回 `403 Forbidden` 或空数组。

## 4. 后台批处理与边缘函数 (Edge Functions)

针对定时任务（如每日风险扫描、周报自动打包）或需要调用第三方 API（如发送微信通知）的场景：
*   不依赖持续运行的 Node.js 服务器。
*   在 Supabase Edge Functions (Deno 运行时) 中编写独立函数。
*   通过 Supabase pg_cron 进行定时触发，或在触发器中通过 HTTP Request 触发。
